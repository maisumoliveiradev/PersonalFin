# ADR-0001 --- Cross-Platform Application Strategy

## Status

Accepted (2026-09-23, SDD-001)

## Context

The product targets Web, Android, and iOS with functional parity and
platform-adapted UX. The team is TypeScript/React-oriented and wants
incremental delivery with future offline-first mobile support.

## Decision to validate before implementation

Prefer an Expo + React Native + React Native Web oriented strategy
unless the foundation spike identifies a material limitation for the
required Web experience.

A monorepo with a dedicated Web framework and shared packages remains
the primary alternative if analytics-heavy Web needs justify stronger
Web specialization.

## Alternatives Considered

1.  Expo / React Native / React Native Web.
2.  Next.js Web + Expo Mobile in a monorepo with shared domain/design
    packages.
3.  Fully separate Web and Mobile applications.

## Decision criteria

-   Web responsiveness and analytics ergonomics;
-   Android/iOS delivery;
-   shared domain and UI potential;
-   developer experience;
-   testing;
-   offline evolution;
-   ecosystem maturity;
-   build/deploy complexity.

## Validation (SDD-001)

| Criterion | Expo + RN Web (1) | Next.js + Expo monorepo (2) |
|---|---|---|
| Web responsiveness / analytics | Adequate. Web-only visualizations can be isolated in `.web.tsx` platform files when dashboards arrive (v0.5.0). | Strongest. Full DOM ecosystem by default. |
| Android/iOS delivery | Same Expo toolchain in both options. | Same Expo toolchain in both options. |
| Shared domain and UI | Domain, contracts, and screens are shared. | Domain and contracts are shared; screens are implemented twice. |
| Functional parity (FR-104) | One UI implementation per feature. | Every feature is built and maintained in two UI stacks. |
| Developer experience | One app, one router, one set of UI conventions. | Two frameworks, two routing models, two styling systems. |
| Testing | One UI stack to test. | Two UI stacks to test. |
| Offline evolution (v0.7.0) | Mobile-local concern; unaffected. | Mobile-local concern; unaffected. |
| SSR/SEO | Not needed: the product is an authenticated application. | Main strength of Next.js, which this product does not require. |
| Build/deploy complexity | One client build pipeline (static Web export + native builds). | Two client build pipelines. |

Option 3 was discarded: it removes shared domain code and duplicates
all product work without a corresponding benefit.

Validated in the foundation spike: the Expo SDK 57 app renders on Web
through React Native Web (dev server and static export), and iOS and
Android bundles compile from the same source.

## Decision

Adopt **option 1**: a single Expo (React Native + React Native Web)
client application targeting Web, Android, and iOS, inside an npm
workspaces monorepo that also contains the API and shared packages.

Concrete structure:

``` text
apps/
  client/          Expo universal app (Web, Android, iOS)
  api/             Application API (see ADR-0005)
packages/
  api-contract/    OpenAPI contract and generated TypeScript types (ADR-0002)
```

Shared domain packages (for example `packages/domain`) are added under
`packages/` by the SDD that introduces the first domain rule, not
speculatively.

## Consequences

-   Each feature has one UI implementation shared across platforms;
    platform differences are isolated with platform-specific files
    (`*.web.tsx`, `*.native.tsx`) rather than separate apps.
-   Web UX is built with React Native primitives. When analytics-heavy
    Web needs arrive, Web-only components can use DOM libraries behind
    `.web.tsx` files.
-   Because the repository is already a monorepo with shared packages,
    moving to option 2 later means adding `apps/web` and superseding
    this ADR, without restructuring the existing packages.
-   Native projects (`ios/`, `android/`) are generated by Expo
    Continuous Native Generation and are not committed or hand-edited.
-   Revisit trigger: if implementing the v0.5.0 analytics on Web through
    React Native Web proves materially limiting, reassess option 2 in a
    new ADR.
